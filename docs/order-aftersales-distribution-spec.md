## 1. 目标与边界

### 1.1 目标

- 形成消费者下单、支付、履约、确认收货、申请售后和退款的可追踪闭环。
- 形成推广员申请、审核、分享归因、等级评估、佣金入账、冻结释放和提现出款闭环。
- 让小程序、运营后台、财务操作和系统任务对同一业务对象展示一致的状态与金额。
- 保留完整订单、售后、佣金、提现和审计历史；重复请求、回调及异步消息不得重复产生业务结果。

### 1.2 本规格包含

- 消费者订单列表、订单详情、下单结果、物流与售后入口。
- 运营订单列表、订单详情、发货和订单异常处理。
- 消费者售后申请与进度、运营审核、退货验收和退款跟踪。
- 推广员资格申请、审核、分享归因、推广关系、等级与佣金规则、佣金账本、提现、风险和审计。
- 核心角色权限、状态机、关键字段、业务规则和可验证验收标准。

### 1.3 本规格不包含

- 商品、购物车、营销活动、会员等级、物流供应商和微信支付的独立完整规格；本规格只定义它们与订单、售后、分销的交互契约。
- 最终数据库 DDL、接口 URL/OpenAPI、工程目录、部署方案和生产容量指标。
- 真实微信支付、退款、商户出款或物流服务开通。原型中的模拟操作不代表真实渠道已接通。

## 2. 事实来源与重要差异

- `docs/architecture.md` 是已确认的技术/领域边界基线；其中明确标为待实施前确认的业务参数仍是 TBD。
- V3 原型页面和 JS 仅说明当前演示交互，不自动构成已批准规则。原型共用浏览器本地数据，支付、退款、物流和提现均为模拟行为。
- 架构定义推广关系最多三级；原型目前按一级佣金演示。规格按“最多三级”作为目标基线，佣金层级与费率仍须运营/财务批准。
- 架构要求下单锁定/预占库存与权益、异步确认退款；原型现状不完整，不能作为正式验收标准。
- 架构规定已提现佣金遇退款进入人工异常处理，不自动扣款或产生负余额；该规则属于基线约束。
- 原型中的示例比例、金额门槛、冻结天数、审核阈值和演示状态均不得作为生产默认值。

## 3. 角色与权限

| 角色 | 允许的业务动作 | 不允许/约束 |
| --- | --- | --- |
| 消费者 | 查看本人订单；在符合规则时取消、确认收货、申请售后；查看本人售后进度；查看本人推广资格、佣金及提现 | 不能读取或操作他人订单、售后、推广关系或收款信息；不能指定服务端认定的价格、退款额、推广归属或佣金 |
| 推广员 | 消费者权限；创建本人有效分享码；查看本人可见团队、佣金账单和提现单 | 推广资格、风险状态和可提现余额由服务端判定；不能修改佣金快照或推广关系 |
| 订单运营 | 查询订单；在权限范围内关闭未支付订单、录入发货信息、查看物流和订单事件 | 不得修改已固化的历史价格/优惠/归因快照；敏感动作需记录操作者、理由和结果 |
| 售后审核员 | 查看售后证据、审核/拒绝、处理退货验收并跟踪退款 | 退款金额不得由客户端或人工绕过规则直接覆盖；审核与支付退款成功是不同状态 |
| 分销运营 | 审核推广申请、维护版本化规则、评估等级、处理推广关系和风控工单 | 佣金调账、关系纠正和规则生效需授权、填写原因并审计；不得改写历史快照 |
| 财务/出款人员 | 审核提现、执行获准通道出款、登记人工转账结果和凭证、处理已提现后退款异常 | 运营批准不等于资金到账；渠道状态未知时不得盲目重复付款 |
| 系统任务/外部渠道 | 超时关单、状态评估、退款/支付/出款结果回传、账本投影和对账 | 所有事件需验签/去重/幂等；外部超时不直接等于失败 |

后台菜单可见性与服务端 API 权限分别控制。以上角色是否由单一账号兼任、审批是否要求双人复核、数据范围和权限点粒度均为 **TBD**。

## 4. 核心对象与状态模型

订单、支付、履约、售后和佣金是相互关联但独立的状态对象。不得用一个订单状态覆盖支付退款、物流或佣金的全部事实。

### 4.1 订单

| 对象 | 建议生命周期 | 说明 |
| --- | --- | --- |
| 订单 | `pending_payment → to_ship → to_receive → completed`；待支付也可 `→ cancelled` | 部分退款保留原订单履约状态，并在退款汇总中表达部分退款；是否另设 `refunded` 终态仅适用于全额退款，具体展示口径待确认 |
| 支付 | `unpaid → paying → paid / failed / closed` | 支付回调以服务端验签、订单号、金额和币种校验为准；状态枚举及失败重试边界待接口契约确定 |
| 履约 | `unfulfilled → shipped → delivered` | 支持单包裹/多包裹、部分发货与物流纠错的策略待确认 |
| 订单快照 | 创建时固化商品/SKU、数量、成交价、优惠分摊、运费、收货信息和推广归属 | 后续编辑商品、地址、优惠或佣金规则不得重算历史订单 |

### 4.2 售后

建议将售后申请类型、审核、退货验收、退款渠道处理分别表达。原型展示的合并状态须在实现规格/API 阶段映射到明确状态。

| 场景 | 建议生命周期 | 规则 |
| --- | --- | --- |
| 仅退款 | `pending → rejected` 或 `approved → refund_processing → refunded / refund_failed` | 审核通过仅表示业务批准；渠道退款确认后才能标记成功 |
| 退货退款 | `pending → rejected` 或 `approved_wait_return → return_in_transit → return_received → refund_processing → refunded / refund_failed` | 退货物流、签收、验收和渠道退款分开记录 |
| 验收不通过 | `return_received → inspection_failed → TBD 后续处置` | 不允许成为无可执行后续动作的死状态；重寄、补充材料、复核、部分退款或关闭由业务决策确认 |
| 取消/关闭 | `pending → cancelled/closed`（如批准） | 谁可取消、已审核后能否取消、超时关闭规则待确认 |

同一订单可有多个售后申请，但同一商品数量和退款金额不得超出订单剩余可售后额度。并发申请的锁定与冲突处理由服务端原子校验。

### 4.3 分销

| 对象 | 建议生命周期 | 说明 |
| --- | --- | --- |
| 推广申请 | `pending → approved / rejected` | 审批人、原因、时间和状态历史可查询；拒绝后的重申限制 TBD |
| 推广资格 | `active ↔ revoked` | 资格与账号启停、风险状态分离；撤销不改写历史订单佣金快照 |
| 推广关系 | `unbound → bound`；受控纠正产生有审计的新版本/事件 | 首次绑定原则；最多三级，链路无环；纠正权限和生效范围待批准 |
| 佣金 | 支付后 `pending → frozen → available → withdrawal_locked → withdrawn` | 冻结期及售后阻断规则可配置但具体数值 TBD；退款通过追加冲正表达 |
| 提现 | `submitted → reviewing/approved → paying → succeeded/failed`；也可能 `→ rejected/cancelled` | 申请锁定余额；明确失败/拒绝释放；结果未知保持处理中并对账 |
| 风险 | `normal / reviewing / frozen` | 与推广资格独立；对分享、已建立关系、佣金结算和提现的影响矩阵待确认 |

## 7. 验收标准

验收使用 Given/When/Then。依赖 TBD 的场景只有在相应规则审批、配置和测试数据明确后才能执行；不得以原型演示值替代审批。

### 7.1 订单验收

| AC-ID | 关联需求 | Given / When / Then |
| --- | --- | --- |
| AC-ORD-01 | REQ-ORD-01/02 | Given 用户、SKU、库存、地址和优惠均有效，When 用户确认提交且请求中携带幂等键，Then 系统按服务端数据创建唯一待支付订单，固定商品行/金额/地址/优惠/归因快照并返回同一订单结果。 |
| AC-ORD-02 | REQ-ORD-01 | Given 提交时商品已下架、SKU 无效、库存不足、优惠失效或用户无权使用，When 服务端校验，Then 不创建可支付订单、不扣减权益，并返回可理解的失败原因。 |
| AC-ORD-03 | REQ-ORD-02 | Given 订单已创建且商品价格/名称、用户地址或佣金规则随后变化，When 用户或运营查看原订单，Then 展示创建时快照，历史金额与推广归属不变。 |
| AC-ORD-04 | REQ-ORD-03 | Given 已支付订单收到同一笔合法支付通知两次，When 服务端处理回调，Then 订单只进入已支付一次，库存/优惠/积分/佣金副作用各只发生一次；伪造签名或金额不一致的通知不改变业务状态。 |
| AC-ORD-05 | REQ-ORD-04 | Given 未支付订单达到已批准的支付时限，When 关单任务执行或恢复重跑，Then 订单只关闭一次并释放对应预占；若渠道支付结果未知，则先查询/对账而不是直接释放后接受重复支付。 |
| AC-ORD-06 | REQ-ORD-05 | Given 订单状态允许用户取消/确认收货，When 用户执行一次或重复点击动作，Then 首次动作只产生一次合法状态变化，后续重复请求返回当前状态且不重复发权益；不允许的状态返回明确提示。 |
| AC-ORD-07 | REQ-ORD-06 | Given 运营具备订单查询权限，When 按订单号、用户、状态和时间筛选并翻页，Then 结果条件一致、总数/页码正确、详情可关联支付与履约事件；无权账号不能通过直接请求获取数据。 |
| AC-ORD-08 | REQ-ORD-07 | Given 订单处于可发货状态且无阻断售后，When 授权运营录入有效承运商和运单信息，Then 创建履约记录并可在消费者端查看；缺字段、重复冲突或存在阻断售后时不产生部分成功发货。 |
| AC-ORD-09 | REQ-ORD-08 | Given 物流 Provider 未接入或无轨迹，When 消费者查看物流，Then 页面明确展示暂无/模拟轨迹，不声称为实时物流信息。 |

| AC-DIS-13 | REQ-DIS-09 | Given 操作员尝试纠正关系、发布规则、调账、审核提现或冻结账户，When 其权限不足或未填写必需理由，Then 操作拒绝；有权限并完成操作时写入完整审计前后值，普通账号不能读取敏感收款资料。 |
| AC-DIS-14 | REQ-DIS-10 | Given 推广员查看本人数据或运营查询推广对象，When 按规定筛选、分页并打开佣金解释链，Then 只返回授权范围内数据，并能从推广归属追踪到订单项、规则版本、佣金流水和退款调整。 |
