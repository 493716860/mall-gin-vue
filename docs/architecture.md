# 微信小程序商城架构方案

## 1. 目标与范围

建设面向单一企业/品牌的微信小程序商城，包含运营后台和面向消费者的小程序。后端采用 Go + Gin 模块化单体，按业务领域划分模块，在保留未来拆分空间的同时避免首期引入微服务治理成本。

本方案是后续工程实施基线，不代表本阶段已经创建或实现这些目录、接口和服务。

**本方案覆盖**
- 商品维护、分类、SKU、库存、购物车、结算、订单、支付、售后退款和物流履约。
- 微信原生客服入口、优惠券/满减、秒杀、拼团、积分/储值。
- 推广员申请审核、最多三级推广关系、等级晋升、佣金核算和账单。
- 管理后台和小程序的 API/认证边界、数据所有权、部署与质量要求。

**本阶段不锁定**
- 物流厂商、具体云环境、佣金比例、等级数值门槛、营销数值规则、提现限额/冻结天数及出款通道的实际开通资格。
- 前端页面原型、具体表结构 DDL、接口字段级 OpenAPI、代码实现与生产容量指标。
- 多商户入驻、跨境交易、拆分微服务。

分销奖励按现金计价的佣金账本核算，并提供微信商户出款与人工银行转账两种提现通道的架构边界；具体费率、限额、冻结天数、资质和出款产品开通情况仍需后续确认。

## 2. 已确认的技术与架构决策

| 领域 | 决策 |
| --- | --- |
| 后端 | Go、Gin、GORM |
| 架构 | 单商户、模块化单体；首期一个 API 服务及异步 worker 进程，可由同一代码库构建 |
| 数据 | MySQL 为业务事实数据源；Redis 用于缓存、限流、短期协调和非权威热点数据 |
| 异步 | RabbitMQ 承载可靠业务事件与后台任务，事务 Outbox 解决数据库提交与消息投递一致性 |
| 后台 | Vue3 + TypeScript，按后台业务功能拆分页面与 API client |
| 小程序 | Vue3 + uni-app；通过独立小程序 API 面向微信客户端 |
| 对象存储 | 腾讯云 COS，通过存储适配层访问 |
| 支付 | 微信支付；回调校验与支付状态以服务端验签结果为准 |
| 分销提现 | 独立佣金账本；推广员选择已启用的微信商户出款或人工银行转账通道 |
| 客服 | 微信原生客服能力；不在首期自建实时聊天系统 |
| 物流 | 通过 Provider 接口隔离；厂商待实施前确认 |
| 本地/首期部署 | Docker Compose；生产环境的云主机、托管数据库及高可用参数待部署阶段确认 |
| 后台认证 | 后台账号登录 + RBAC + 关键操作审计 |
| 消费者认证 | 微信登录；服务端维护商城用户身份，不把微信会话凭据当作业务授权本身 |

## 3. 系统上下文与组件

```text
运营人员
  └─ Vue3 Admin ── HTTPS /api/admin/v1 ──┐
                                        │
微信用户                              Go/Gin API
  └─ uni-app 小程序 ─ HTTPS /api/mini/v1 ┘
                                           ├─ MySQL（领域数据、事务 Outbox）
                                           ├─ Redis（缓存、限流、短期协调）
                                           ├─ RabbitMQ（事件、重试、死信）
                                           ├─ 微信登录 / 微信支付 / 微信原生客服
                                           ├─ 腾讯云 COS（图片与凭证）
                                           └─ Logistics Provider（待选供应商）

Go Worker（同一代码库）
  ├─ 消费 RabbitMQ 事件
  ├─ 执行 Outbox 发布、通知、超时处理及周期性等级评估
  └─ 通过领域应用接口处理任务，不复制业务规则
```

API 与 Worker 可作为不同进程部署，但共享模块代码和配置模型。初期无需为每个业务模块单独部署服务；只有在团队边界、负载或可靠性目标明确后，才评估独立拆分。

## 4. 仓库目录建议

顶层按工程入口、业务后端、客户端、接口契约和运行资源分组。后端代码按业务模块归类，不建立跨领域的巨型 `controllers`、`services`、`models` 目录。

```text
.
├── cmd/
│   ├── api/
│   │   └── main.go
│   └── worker/
│       └── main.go
├── internal/
│   ├── bootstrap/                 # 组装依赖、路由、消费者与生命周期
│   ├── platform/                  # Gin、GORM、Redis、RabbitMQ、COS、日志等技术适配
│   ├── shared/                    # 少量跨模块值对象、错误、时钟、分页等稳定抽象
│   └── modules/
│       ├── identity/              # 后台身份、RBAC、消费者微信身份
│       ├── member/                # 会员资料、地址、积分/储值账户
│       ├── catalog/               # 商品、类目、SKU、上下架
│       ├── inventory/             # 库存台账、预占、释放、扣减
│       ├── cart/                  # 购物车
│       ├── pricing/               # 价格与营销试算、优惠分摊
│       ├── order/                 # 订单、订单项、状态机、超时关闭
│       ├── payment/               # 支付单、微信支付适配、回调处理
│       ├── aftersales/            # 退货退款、售后审核与退款协作
│       ├── fulfillment/           # 发货、包裹、物流 Provider
│       ├── customer_service/      # 客服入口、服务记录/运营配置
│       ├── marketing/             # 优惠券、满减、秒杀、拼团
│       ├── distribution/          # 推广员、关系、等级、佣金账本
│       ├── content/               # Banner、公告等商城展示内容
│       └── audit/                 # 后台敏感操作审计
├── web/
│   ├── admin/                     # Vue3 + TypeScript 运营后台
│   └── miniapp/                   # Vue3 + uni-app 微信小程序
├── api/
│   └── openapi/
│       ├── admin.yaml
│       └── miniapp.yaml
├── migrations/                    # 按模块/版本管理的数据库迁移
├── configs/
│   └── config.example.yaml        # 非敏感配置样例，不放真实密钥
├── deploy/
│   └── compose.yaml               # 本地依赖与应用编排样例
├── docs/
│   └── architecture.md
└── go.mod
```

每个后端业务模块采用一致但可按需要精简的内部布局：

```text
internal/modules/order/
├── http/                  # 模块路由、请求/响应 DTO、鉴权声明
├── application/           # 用例编排、事务边界、模块端口
├── domain/                # 实体、值对象、规则、状态机、领域事件
└── infrastructure/        # GORM repository、外部适配实现
```

**依赖约束**
- HTTP 层只做协议解析、身份/权限上下文、参数校验和响应转换；不直接访问 GORM。
- `application` 编排用例并定义需要的 repository/provider 接口；领域规则留在 `domain`。
- `infrastructure` 实现接口，不能被其他模块直接引用。
- 跨模块协作优先通过明确的应用接口或版本化领域事件；禁止跨模块读写对方的表或依赖其 ORM Model。
- `shared` 只放真正通用且稳定的技术无关概念；商品、订单、会员等业务模型不得放入共享包。
- 模块可以共用同一个 MySQL 实例，但表的写入权唯一归属一个模块。跨模块工作流通过应用编排/事件衔接；需要一致提交的核心交易优先保持在同一事务边界内。
- `platform` 不承载促销、佣金等业务判断，也不作为无边界的公共工具箱。

后台页面可在 `web/admin/src/modules/<feature>/` 按商品、订单、售后、营销、分销、会员和权限组织。小程序按首页、商品、购物车、订单、会员/分销等功能组织页面。两端共享 API 契约和设计规范，但不共享服务端信任逻辑。

## 5. 业务模块边界

| 模块 | 所有权与职责 | 主要协作 |
| --- | --- | --- |
| identity | 后台账号、角色、菜单/API 权限；消费者微信身份映射 | audit、所有管理端模块 |
| member | 消费者资料、收货地址、会员账户；积分/储值账户及明细 | order、marketing、distribution |
| catalog | 类目、商品、SKU、售价信息、上下架与媒体引用 | inventory、pricing |
| inventory | SKU 可售量、预占量、库存流水、预占释放规则 | order、marketing |
| cart | 用户购物车条目和失效清理 | catalog、pricing |
| pricing | 商品价格、优惠规则组合、优惠分摊和下单价格快照 | catalog、marketing、member、order |
| order | 订单及订单项、买家/地址/价格快照、订单状态机 | inventory、payment、aftersales、fulfillment、distribution |
| payment | 支付单、渠道交易号、回调验签、退款请求和渠道结果 | order、aftersales |
| aftersales | 售后申请、退款/退货流程、退款金额核验 | order、payment、inventory、distribution |
| fulfillment | 发货包裹、物流单号、轨迹查询和 Provider 适配 | order、COS |
| customer_service | 小程序客服入口配置、必要的服务/转接记录 | identity、member；对接微信原生客服 |
| marketing | 优惠券、满减、秒杀、拼团活动及活动库存规则 | pricing、inventory、order、member |
| distribution | 资格申请、推广关系、等级规则/评估、佣金账本与结算 | member、order、aftersales |
| content | 首页 Banner、公告等可运营展示内容 | catalog、web clients |
| audit | 管理端敏感操作审计记录、操作者、目标、结果 | identity、管理端用例 |

### 5.1 核心业务不变量

- 订单提交时固化商品名称、SKU、单价、数量、优惠分摊、收货信息及分销归属快照；历史订单不随商品或规则编辑而改变。
- 商品可售库存以 MySQL 事务更新和库存流水为准。Redis 缓存或锁不能作为库存正确性的唯一保障。
- 订单、支付、售后、拼团、秒杀、佣金均使用明确状态机；状态变更必须检查合法前置状态并留下可追踪记录。
- 微信支付回调、退款回调和消息消费按事件/业务键幂等；重复通知不得重复支付、退款、扣库存或记佣金。
- 优惠、积分/储值和佣金需保留可解释的明细/账本，不能仅通过覆盖余额或重新计算历史订单来对账。
- 金额使用整数最小货币单位（例如分）或明确精度的 decimal 类型；不得使用二进制浮点数做金额运算。

## 6. 关键数据模型

以下为逻辑实体与归属建议，不是最终 DDL。每个实体应包含主键、创建/更新时间及必要的状态版本字段；涉及金额的表存储币种和明确定义的金额单位。

| 归属 | 主要实体 |
| --- | --- |
| identity | `admin_account`、`role`、`permission`、`account_role`、`role_permission`、`consumer_identity` |
| member | `member`、`member_address`、`member_account`、`account_ledger` |
| catalog | `category`、`product`、`sku`、`product_media` |
| inventory | `sku_inventory`、`inventory_reservation`、`inventory_ledger` |
| cart | `cart`、`cart_item` |
| marketing | `campaign`、`coupon_template`、`member_coupon`、`promotion_rule`、`flash_sale_item`、`group_event`、`group_member` |
| order | `order`、`order_item`、`order_discount_allocation`、`order_status_history` |
| payment | `payment_transaction`、`payment_notification`、`refund_transaction` |
| aftersales | `aftersale_case`、`aftersale_item`、`aftersale_status_history` |
| fulfillment | `shipment`、`shipment_item`、`logistics_tracking_event` |
| distribution | `promoter_application`、`promoter_profile`、`referral_relation`、`distribution_tier`、`tier_rule_version`、`commission_rule_version`、`commission_order_snapshot`、`commission_account`（账本汇总投影）、`commission_ledger`、`payout_channel_profile`（令牌/脱敏资料引用）、`commission_payout_request`、`commission_payout_attempt` |
| integration | `outbox_event`、`inbox_event`、`scheduled_job`（可按部署实现方式合并或调整） |
| audit | `admin_audit_log` |

**关键约束建议**
- 对外订单号、支付渠道交易号、退款渠道单号、优惠券领取资格、推广关系和账本业务来源设置唯一约束，防止并发请求产生重复业务事实。
- `referral_relation` 对被推广用户设置唯一约束以保证首次绑定；保存绑定来源、时间、绑定推广员及有效状态。
- 库存流水、会员资金/积分流水、佣金流水采用追加式明细；纠错以冲正记录表达，不删除已生效历史。
- 佣金账户只核算商城应付推广佣金，与会员积分/储值账户分离；它不是可充值、转账或用于商城消费的通用钱包。
- `commission_account` 是 `commission_ledger` 的可重建汇总投影，不是独立资金事实来源；提现锁定、出款和失败释放均需有对应账本流水与提现单。
- `order_item` 与优惠分摊保存 SKU 数量、成交单价和分摊金额，以支持部分退款、佣金基数和财务核对。
- 佣金记录关联订单项/推广层级/规则版本，保留当时的比例、基数和金额，避免规则变更导致历史金额漂移。
- 高并发查询所需索引、分区和归档策略在容量评估后确定，不预先假设业务量。

## 7. API 与认证边界

### 7.1 API 分面

- 运营后台：`/api/admin/v1/...`，后台账号身份，按角色和权限点授权；管理端接口不得通过隐藏按钮替代服务端鉴权。
- 小程序：`/api/mini/v1/...`，微信登录后发放商城访问凭证；请求只能访问当前用户可见的数据，不能信任客户端传入的用户 ID、价格或佣金金额。
- 第三方回调：独立的 `/api/webhooks/wechat/pay` 等地址；按官方协议验签、校验商户与金额、限制重放，返回协议要求的应答。回调不使用普通用户 JWT。
- 文件：后端鉴权后签发短时 COS 上传凭证/预签名地址；上传完成后校验对象归属、类型、大小和用途。
- 接口契约放在 `api/openapi/`，管理端和小程序 API schema 分开维护，版本化变更。

### 7.2 协议约定

- 统一 JSON 响应、错误码、请求追踪 ID 和时间格式；错误响应包含稳定业务码、可读提示、追踪 ID，不泄漏堆栈、密钥或个人敏感数据。
- 列表接口统一分页和排序白名单；大体量流水/事件列表优先采用游标分页。
- 创建订单、发起退款、领取限量权益等非天然幂等的操作接受幂等键。服务端保存幂等结果或依赖唯一业务约束实现安全重放。
- 金额、商品、优惠资格、库存和订单状态以服务端重新读取与计算结果为准。
- 后台写操作按权限点控制；导出、退款审核、佣金调整、角色授权、敏感配置等操作记录审计。
- API 限流按身份、IP、接口类别设定；登录、优惠领取、拼团、秒杀和回调入口加强防刷与重放保护。

### 7.3 登录与权限

- 小程序通过微信登录凭证换取服务端会话；业务用户 ID 与 `openid/unionid` 映射受保护。若需跨应用统一身份，是否要求开放平台 `unionid` 在接入前确认。
- 管理端使用独立后台账号，不复用消费者身份。密码使用适当的强哈希存储，登录和敏感操作实施速率限制；会话过期、刷新、登出和账号禁用需要可控。
- RBAC 至少包含账号、角色、权限点和角色分配；菜单展示权限与 API 操作权限分别核验。多角色合并规则必须确定且可审计。
- 仓库/门店级数据权限不纳入单商户默认模型；若未来加入线下门店，再扩展数据范围权限而非绕过 RBAC。

## 8. 核心流程

### 8.1 商品下单与库存

1. 客户端提交 SKU、数量、地址引用、优惠选择和幂等键。
2. 服务端重新读取商品状态、价格、会员资格与营销资格；调用库存模块进行可售校验。
3. 交易事务建立订单/订单项/优惠分摊快照，预占库存、锁定优惠券/积分等权益；通过 Outbox 写入订单已创建事件。
4. 事务成功后创建微信支付单，返回支付参数；创建失败按补偿规则关闭订单并释放预占。
5. 支付成功回调经验签、金额核验和幂等处理后更新支付/订单状态，Outbox 发布支付成功事件。
6. 超时未支付由持久化任务或可靠延迟机制关闭订单、释放库存和优惠。RabbitMQ TTL/DLX 可用于延迟投递，但订单状态/超时扫描仍需可恢复机制，不依赖单一插件。

涉及订单、库存、优惠等多个模块时，优先通过应用层工作流编排，并明确每一步成功、失败和补偿动作；避免长期持有数据库事务调用微信等外部网络。

### 8.2 支付、发货与售后

- 支付回调：验签及商户/订单/金额/币种核验；将通知编号或渠道交易号写入唯一约束；事务内更新支付状态和订单状态、追加 Outbox。业务成功后应答微信，后续副作用由事件消费执行。
- 发货：运营录入包裹/物流信息或调用物流 Provider；订单进入已发货；物流查询结果按外部事件 ID/时间去重并保存轨迹。
- 售后：校验订单项可退数量、已退金额与当前售后状态；审核通过后创建退款请求；支付模块调用微信退款接口并异步确认最终结果。
- 退款成功后追加退款账本、释放/回补适用权益、处理库存策略并按已退款商品金额冲减分销佣金。退货商品是否重新入库、优惠如何按部分退款重分摊由运营规则明确并通过快照/明细可追溯。
- 所有外部调用均需超时、有限重试、幂等键、状态查询/对账补偿路径；不可将“接口返回超时”直接等价为支付或退款失败。

### 8.3 营销结算

- 结算模块统一输出商品原价、可参与活动、优惠试算、优惠分摊及应付金额；订单保存计算结果，支付与售后使用同一份订单快照。
- 优惠券/满减校验适用商品、门槛、时段、用户限额及互斥规则，并原子地锁定/核销资格。
- 秒杀以库存原子预占、用户限购和请求限流为关键控制；Redis 可作快速挡板，最终超卖防护仍由数据库条件更新/唯一约束兜底。
- 拼团保存团状态、截止时间、成团人数与成员订单关联；重复参团、成团并发、过期取消与退款需走显式状态机。
- 积分/储值变动走会员账本；抵扣和退款按下单快照做精确回滚/冲正，避免直接改余额而没有来源明细。

### 8.4 在线客服

- 小程序展示微信原生客服入口和官方要求的会话上下文，不自行伪造微信客服能力或采集超出授权范围的数据。
- 商城保存必要的客服入口配置、客服来源/订单关联和获准获取的会话服务事件；微信侧会话内容、客服工作台及留存能力以已开通的微信产品接口和权限为准。
- 若未来需要平台内会话分配、客服在线状态或全量聊天留存，应作为单独范围评估自建实时消息系统或第三方 SaaS，不与当前原生客服入口混为一体。

## 9. 分销与佣金设计

### 9.1 资格、绑定与等级

- 用户提交推广员申请，后台审核通过后生成推广员资料；审核拒绝、撤销资格及再次申请均保留状态历史和操作者。
- 推广关系最多三级；推广归因首次绑定后，普通推广链接不能覆盖已有关系。后台纠正绑定如确有业务需要，应增加独立权限、理由、前后值审计和防止循环关系校验。
- 推广关系建立时检查推广员有效资格、被推广人身份和自我邀请等异常情形，并保证链路无环、层级不超过上限。
- 运营后台配置普通/银牌/金牌等级及对应权益。升级条件可配置为累计有效销售额、有效拉新人数、自购金额中的一个或多个，并明确 AND/OR 组合、评估周期、统计口径、退款回滚、升降级和规则生效时间。
- 统计指标必须有确定定义。例如“有效销售额”应基于已支付并确认收货的商品净额扣除退款；“有效拉新”按满足去重条件的新用户计数；“自购金额”按本人实际支付净额计算。最终口径由运营配置/验收确认。
- 等级评估采用可重跑的周期任务或事件更新；每次评估保存输入统计窗口、命中规则版本、结果和原因，便于解释等级变化。

### 9.2 归因与佣金

- 下单时从买家推广关系解析最多三级上级，并将推广员 ID、层级、归因规则版本固化到订单/佣金快照；后续关系调整不追溯改写已下单订单。
- 佣金规则按推广员等级和关系层级配置比例/权益、有效期及适用范围。规则修改须版本化；订单适用的比例与佣金金额在业务约定的锁定时点固化，避免后台修改影响历史订单。
- 佣金基数为订单商品实付净额，扣除已退款部分，不含运费。若存在跨 SKU 优惠，使用订单优惠分摊快照分配基数，支持部分退款按对应商品重新核算。
- 支付成功后可记为待结算；确认收货后按订单快照核算并进入冻结期。冻结期按后台规则配置，期满且相关订单无阻断性售后后释放为可提现佣金。未完成、取消或全额退款的订单不产生可提现佣金。
- 冻结期前发生退款时调整待结算/冻结金额；已提现后发生退款时只登记异常并冻结账户待财务人工处理，不自动扣款或静默产生负余额。
- `commission_ledger` 为追加式资金账本，记录待结算、冻结、释放、提现锁定、出款、失败释放、退款调整等业务变动；每笔关联推广员、订单/订单项或提现单、层级、基数、规则版本、幂等键、时间及必要的冲正关联。
- `commission_account` 汇总展示待结算、冻结、可提现、提现中、已提现及待人工处理金额；余额由账本投影得出并可重建。提现申请时原子锁定相应可提现金额，防止并发超额申请。

### 9.3 佣金账户与真实提现

- 推广奖励以现金计价的佣金进入独立佣金账本，不以商城积分替代现金佣金。积分继续作为独立会员权益，不能被展示为可提现现金。
- 佣金账户是商城内部记录应付推广佣金的业务子账，不支持充值、用户间转账或商城消费。用户只能将满足条件的“可提现”佣金提交提现申请；账面金额不代表商城提供通用储值或支付账户。
- 推广员从当前已启用且其收款资料验证通过的渠道中选择一种：微信商户出款，或人工银行转账。出款由 `PayoutProvider`/财务执行适配边界隔离；微信商户出款的实际产品能力、商户资格、实名要求与合规条件必须在接入前核实。
- 提现申请按配置的最低金额、单笔/周期限额、账号状态、风控检查和可提现余额校验。小额申请在风险检查通过且渠道支持自动处理时自动审批；大额申请进入人工审核。微信通道仅在资格、产品和风控均允许时自动出款；银行转账由财务执行并登记付款结果/凭证，自动审批不等于银行款项已自动到账。
- 提现单建议状态为 `submitted`、`reviewing`、`approved`、`paying`、`succeeded`、`failed`、`canceled`。申请成功时先锁定佣金；出款成功后记为已提现；出款明确失败或审核取消时通过账本释放锁定金额。超时/结果未知时保持处理中并查询/对账，不直接重试可能导致重复付款的请求。
- 每笔出款使用唯一提现单号/幂等键，保存通道、通道流水号、金额、状态时间、审核人与凭证引用。通道回调需验签、去重；人工银行付款需二次核对收款人脱敏信息、金额和凭证，所有状态改变均写审计记录。
- 确认收货后佣金先进入可配置冻结期；冻结期间若有关联售后未完成则继续冻结，售后结束后按规则释放或冲减。冻结天数、最低提现额、小额自动审核阈值、单笔/日累计限额由后台配置，具体值由运营/财务上线前确认。
- 收款资料优先由已启用通道完成实名及账户验证；系统仅保存通道令牌/资料引用、脱敏展示信息和审计所需字段。人工银行转账所需完整账户资料应由受控财务系统或受限加密存储管理，不进入普通业务日志或广泛可访问的业务表。
- 已提现佣金对应订单发生退款时，系统生成退款后佣金异常单并冻结待处理账户，由财务逐案决定冲抵未来佣金、线下追偿或其他合规处理；处置、理由、审批人与账本调整均需记录。系统不自动扣用户资金，也不静默形成负余额。
- 提现可通过小程序接口查询佣金账户/账单并发起或查询申请；管理端提供审核、风控处置、人工银行付款登记、凭证查询与对账能力。精确字段和 API schema 在接口设计阶段定义。

### 9.4 防错与风控

- 关系绑定和订单佣金快照以唯一键/幂等请求保护；消息重复消费不得生成多条有效佣金。
- 对自购刷单、同设备批量注册、退款套利、推广关系循环、异常高频领取和佣金提现进行规则化风控与运营复核。
- 后台可查询订单到佣金的完整解释链：归属关系、层级、规则版本、佣金基数、退款调整及状态迁移。
- 提现还需检查账户冻结状态、收款资料验证、申请频率、单笔/周期限额、重复申请和异常设备/身份；高风险申请转人工复核。
- 推广资格、佣金比例、等级权益及推广层级需在上线前进行法律合规和平台规则审查；禁止以组织拉人头或不合规多层返利方式设计。

## 10. 异步消息与一致性

- 同一业务数据库事务同时写领域数据和 Outbox 记录；独立发布器投递 RabbitMQ。发布成功后标记 Outbox，失败采用退避重试并告警。
- 消费者使用 Inbox/唯一事件键或业务唯一约束实现至少一次投递下的幂等；消息确认发生在业务处理和持久化成功之后。
- RabbitMQ 按业务事件设置交换机、队列、重试/死信策略；毒消息进入 DLQ 并可追踪、人工/工具安全重放。重放仍必须经过幂等校验。
- 消费逻辑短小、可重试；耗时任务使用任务状态、超时、重试上限和补偿，不在消息回调中无限等待外部服务。
- 需要跨模块最终一致的流程采用 Saga/显式工作流状态和补偿操作；明确“处理中”可观测，不以分布式锁代替业务状态机。
- 对支付、退款、库存、营销权益、佣金定期执行内部账与渠道/库存对账，差异进入人工处理队列并留审计记录。

## 11. 安全、隐私与审计

- 微信密钥、支付商户证书、COS Secret、数据库密码等只从受控密钥管理/部署 Secret 注入；示例配置仅含占位符，禁止提交凭据。
- API 使用 HTTPS；配置请求体大小、超时、CORS 白名单、可信代理和安全响应头；外部回调仅接受官方要求的签名协议。
- 对手机号、地址、openid、支付信息实施最小化采集、按需展示/脱敏、传输保护、访问审计和保留期限管理。
- 提现收款资料按最小化原则处理；展示脱敏，敏感字段只向经授权的财务人员开放。通道令牌、出款凭证引用和提现审计数据设定访问控制及留存策略。
- 参数按类型/范围校验，输出编码，数据库使用参数化查询；上传文件校验 MIME/扩展名/体积并隔离未确认对象。
- 后台账号具备最小权限、禁用与会话撤销能力；退款审核、佣金规则/人工调账、提现审核、银行付款登记、权限变更和敏感数据导出必须审计。
- 生产日志不记录 access token、支付密钥、完整身份证/支付凭证；安全事件和审计日志设置不可随意修改的保留策略。

## 12. 可观测性与运行

- 结构化日志统一带 `request_id`、`trace_id`、模块、操作者/消费者身份（脱敏后）和业务关联 ID；消息消费保留 event ID 与重试次数。
- 暴露存活与就绪检查。就绪检查依赖的服务范围应明确，避免短暂的非关键依赖故障导致所有 API 被摘除。
- 核心指标包括请求量/延迟/错误率、MySQL 连接与慢查询、Redis 状态、RabbitMQ 积压/DLQ、支付回调失败、未支付超时、库存冲突、退款时长、佣金对账差异、提现处理中时长/失败率及待人工审核量。
- 配置按环境分离；开发环境通过 Compose 启动 MySQL、Redis、RabbitMQ，应用可本地调试或容器运行。COS、微信支付等外部服务凭据不写入 Compose 样例。
- 数据库迁移有版本记录、备份与恢复演练；破坏性 schema 变更采用兼容性扩展/迁移/收缩步骤。
- 生产 HA、RPO/RTO、水平扩容、告警阈值、日志保留时长及备份周期需在明确业务规模和云环境后制定。

## 13. 测试策略

- 单元测试：价格/优惠分摊、订单状态机、库存规则、等级评估、佣金冻结释放、提现状态迁移和退款人工异常；使用固定时钟和可控依赖。
- 模块集成测试：GORM repository、事务边界、唯一约束和迁移，在隔离的 MySQL/Redis/RabbitMQ 环境验证。
- API 契约测试：管理端与小程序分别校验认证、权限、字段校验、错误结构和向后兼容。
- 消息测试：Outbox 重试、重复投递、乱序/延迟事件、DLQ 和安全重放。
- 并发测试：限量秒杀、库存预占、优惠券领取、订单幂等、支付/退款重复回调、佣金重复结算和并发提现余额锁定。
- 端到端测试：下单支付、发货、售后退款、部分退款、拼团、佣金冻结/释放及双通道提现；验证出款成功、失败释放、重复回调及已提现后退款人工处置；第三方使用沙箱或可替换模拟 Provider。
- 安全测试：越权、用户间数据隔离、回调伪造/重放、敏感信息日志泄漏、上传限制及限流。

## 14. 实施顺序建议

1. 建立 Go 工程基线、模块模板、配置/日志/错误处理、数据库迁移、Compose 开发依赖和 CI 检查。
2. 实现后台账号/RBAC、微信用户登录、审计、商品/SKU、媒体上传与库存基础能力。
3. 实现价格试算、购物车、订单、库存预占、微信支付回调、超时关单与对账。
4. 实现物流 Provider、售后退款、会员账户及优惠券/满减；完成退款与部分退款规则核验。
5. 实现推广员申请、关系绑定、分级评估、佣金账本/账户投影、冻结释放、双通道提现、审核/冲正和对账，再开放佣金展示/提现入口。
6. 实现秒杀、拼团、积分/储值和客服运营能力，逐项压测并验证风控。
7. 完善生产部署、安全审查、故障演练、备份恢复和灰度发布。

每阶段先完成 API 契约、数据所有权、状态机和验收用例，再并行开发前后端；涉及规则或钱款的能力需运营/财务/法务共同验收。

## 15. 验收清单与实施前待确认

**架构验收**
- 业务代码按领域模块组织，模块拥有自己的模型、仓储实现和迁移边界。
- 管理端与小程序的 API/身份边界独立，所有授权在服务端执行。
- 订单、库存、优惠、支付、售后和佣金有清晰状态机、幂等约束、失败恢复与审计。
- 推广关系最多三级且首次绑定规则可执行；等级条件、费率、佣金账本和退款冲正均可解释、可复算。
- 佣金与积分/储值明确隔离；提现支持配置冻结、小额自动/大额审核、双通道选择、出款失败释放和已提现后退款人工处置。
- 外部支付、COS、物流、客服通过明确适配边界接入；非已确认供应商保持可替换。
- Compose 开发依赖、配置/密钥、迁移、日志/指标、备份与测试要求均有负责模块和验收项。

**编码前由业务/运营确认**
- 物流查询/电子面单供应商与微信小程序类目、支付商户/退款权限、COS 区域与上传策略。
- 推广归因是否允许后台纠正、推广链路各层级的订单归属优先级，以及违规订单处理。
- 等级统计周期、有效销售额/新客/自购口径、升级和降级策略、规则生效时点。
- 各等级 × 各推广层级费率、营销互斥与优惠分摊、部分退款的优惠和库存恢复规则。
- 佣金冻结天数、小额自动审核阈值、最低提现额/限额、人工银行转账的财务凭证流程及人工处理提现后退款的具体财务政策。
- 微信商户出款的可用产品、商户资质、实名/税务要求和实际开通条件；须以正式接入时核验结果为准。
- 积分与储值的有效期、退款策略、财务核算及相关监管要求。
- 微信原生客服授权可用的数据范围、客服运营流程和消息留存要求。
- 首期预计并发、数据量、可用性目标、RPO/RTO 和生产部署平台。
