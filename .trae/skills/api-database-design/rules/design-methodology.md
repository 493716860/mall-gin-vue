# 需求到技术设计推导方法（P0）
1. 读取 REQ/BR/PAGE/AC、原型字段与现有 API/DDL，列出确认状态和风险。
2. 对每个用户动作标记主体、输入、输出、授权、前置条件、成功/失败、是否写入状态。
3. 以操作的业务边界决定 API 粒度，避免把每个按钮机械映射成接口；复用已有接口并明确 operationId。
4. 从持久化事实推导业务对象、唯一业务标识、关系、历史快照/流水与数据所有者，不为纯展示字段建表。
5. 对状态变更设计状态机、原子步骤、事务、幂等、锁/约束和外部依赖；区分同步结果与最终一致。
6. 设计错误码、HTTP 状态、鉴权、资源归属、兼容性及异常恢复。
7. 建立 REQ→API→DTO→TABLE/COLUMN→状态/事务→AC 映射，逐项检查遗漏与冲突。
8. 输出 OpenAPI、SQL Migration、数据字典、设计说明、示例和人工待确认项。
不得把推测业务规则当成已确认事实。简单 CRUD 用 L1，普通状态流程用 L2，资金/库存等高风险用 L3。
